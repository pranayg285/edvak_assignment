# edvark_assignment

## Overview
The system processes a batch of 40 sample messages and produces a structured result for each message. It combines an LLM-based message classifier with deterministic rules and clinic-data tools so that key decisions—especially emergency escalation and refill eligibility—are not left entirely to free-form model output.

For each message, the agent generates fields such as:
- id and patient_id
- intents
- urgency (emergency, urgent, or routine)
- actions
- routed_to
- tool_calls
- reply_draft
Patient identity is kept unconfirmed when the available information is insufficient to verify the sender. The system also evaluates its output against the supplied sample labels, including prohibited-action (must_not) checks.

## Architecture and workflow
1. Load and validate data — Read the synthetic patient, medication, appointment, clinic configuration, message, and label JSON files.
2. Classify the message — Use the Groq API and a configured supported model to extract intents, medication names, appointment requests, clinical concerns, language, and suspicious instructions in a structured response.
3. Apply urgency rules — Run deterministic checks for emergency indicators and combine them with the classifier result. Safety-critical emergency handling should not be overridden by a routine LLM classification.
4. Resolve identity and privacy — Look up candidate patients and verify sender details before exposing patient-specific information or taking patient-specific actions. Caregiver authorization is checked where applicable.
5. Call relevant clinic functions — Depending on the request, retrieve medication and appointment information, check refill eligibility, find appointment slots, or handle appointment operations.
6. Choose actions and routing — Map the message to the required action vocabulary and route it to the appropriate clinic queue or staff member. When a request cannot be safely completed, route it for human review rather than assuming success.
7. Draft a reply and save results — Produce a structured result for every message and evaluate the batch against the supplied labels.

## Technology stack
- Python — Application logic, rules, data processing, and evaluation.
- Groq API — Hosted inference for message classification.
- Configured LLM — GPT-OSS-120b.
- JSON — Synthetic clinic records, input messages, labels, and structured agent output.
- FastMCP — Exposes clinic operations as MCP tools, including patient lookup, verification, medication/refill checks, appointment operations, urgency assessment, routing, and reply drafting.
- Regular expressions and deterministic Python rules — Emergency indicators, identity-related checks, and policy guardrails.
- Python evaluation scripts — Batch metrics and checks for prohibited actions.

## Challenges and how they were addressed
1. Combining LLM flexibility with predictable safety behavior

Challenge: A language model is useful for understanding varied wording, but should not be the sole authority for emergency escalation or policy-sensitive actions.

Approach: Use the LLM for structured intent extraction and deterministic rules for safety-critical checks. Emergency indicators are assessed separately so that a routine LLM label does not silently suppress an emergency signal.

2. Patient identity and privacy

Challenge: A sender may provide a name or date of birth without enough information to securely establish identity. A relative may also ask for information about another patient.

Approach: Separate patient lookup from identity verification, preserve patient_id: null when verification is insufficient, and check caregiver authorization before handling caregiver requests. This can produce a patient-ID mismatch against a permissive sample label, but it avoids treating unverified identity as established.

3. Refill eligibility and prohibited actions

Challenge: A request to refill a medication does not automatically mean a refill can be prepared. Remaining refills, controlled-medication rules, refill timing, and visit requirements can change the correct action.

Approach: Retrieve the patient's medication records, identify the requested medication, and call the refill-eligibility check before selecting an action. The workflow was tightened to fail safely: only a positively eligible result should permit prepare_refill_for_approval; denied, ineligible, or ambiguous results should be routed for appropriate review. This helped eliminate the final reported must_not violations.

4. Matching medication names from natural language

Challenge: Users may mention brand/generic names or different medication-name fields, so exact matching can fail.

Approach: Compare the message text and extracted medication names against the medication records, while retaining a conservative fallback when a requested medication cannot be identified reliably.

5. Appointment scheduling and conflicts

Challenge: A requested time may be unavailable, conflict with an existing appointment, or fall when a provider is unavailable.

Approach: Centralize scheduling logic in AppointmentManager, including provider availability and conflict checks. Offer alternatives when the requested slot cannot be booked instead of claiming that an appointment was made.

6. Evaluation and debugging

Challenge: A batch can have strong urgency results while still missing expected actions or disagreeing with expected patient IDs.

Approach: Build a repeatable evaluator and a failure-inspection script. Use per-message differences and must_not checks to identify concrete defects, then rerun the full batch after changes rather than relying on a few successful examples.

## Evaluation results
Evaluation was run against the 40-message sample set supplied with the assignment.

| Metric | Result |
|---|---:|
| Messages evaluated | 40 |
| Urgency accuracy | **40/40 (100.0%)** |
| Emergency recall | **5/6 (83.3%)** |
| Exact action-set accuracy | **23/40 (57.5%)** |
| Action precision | **60.8%** |
| Action recall | **66.0%** |
| Action F1 | **63.3%** |
| Patient ID mismatches | **0** |
| `must_not` violations | **0** |

## Interpreting the metrics
- Urgency accuracy (100%) means all 40 predictions matched the evaluator's accepted urgency labels.
- Emergency recall (5/6) is a separate metric that measures how many cases counted as emergency cases by the evaluator were detected as emergency. M006 accepts both urgent and emergency; the agent classified M006 as urgent. That classification is accepted for the general urgency-accuracy metric, but the evaluator's emergency-recall calculation still reports 5/6. Therefore, the two metrics are not contradictory: they use different criteria.
- Exact action-set accuracy (57.5%) means the complete predicted action set exactly matched the expected action set for 23 of the 40 messages. Partial matches are not counted as exact matches.
- Action precision, recall, and F1 summarize action-level matches rather than requiring the entire set to be identical.
- Zero patient ID mismatches means all 40 outputs matched the reference labels for patient identity.
- Zero must_not violations means the evaluator did not find any prohibited actions in the generated outputs. This is an important safety result, but it does not mean every expected action was predicted correctly.

## Setup

1. Create and activate a virtual environment
From the project directory in Windows Command Prompt:

python -m venv .venv

.venv\Scripts\activate

2. Install dependencies
Install the dependencies listed in your requirements.txt if the repository contains one:

pip install -r requirements.txt

3. Configure environment variables
Create a .env file in the project root:

GROQ_API_KEY=your_groq_api_key

GROQ_MODEL=your_supported_groq_model_id

4. Validate the data

python validate_json.py

5. Run the agent and evaluation

- python agent.py
- python evaluate_agent.py

The exact output paths depend on the current script configuration. The agent may write agent_output.json, and the evaluator may write evaluation_report.json.
